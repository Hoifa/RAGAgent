# 工程复盘草稿

本稿由 AI 根据实际开发记录整理。候选人的个人理解、学习收获和独立修改尚待本人据实补充，不将 AI 的工作自动计为个人贡献。

## 最难的问题与实际改进

真实 Qwen 调用暴露了 Mock 不能证明的问题：模型可能跳过原文读取、遗漏正文引用标记、在冲突时只追问日期，或把读取失败解释成资料不足。仅有结构正确和状态匹配不足以判断可靠性。

改进包括将被拒绝的行动与具体修复要求回传、显式列出可引用证据、检查冲突查证是否发生，以及区分工具未恢复与资料不存在。校验保守地阻止错误结果，仍由模型决定下一动作，避免编写按用例输出答案的脚本。

检索也出现了相反的风险：为保证文档多样性而每份文档只优先取一段，导致同一通知的关键条款被排除。改为相关性与软多样性平衡后，同一个实际查询中的规则及替代依据召回从 0/2 改为 2/2。该实验规模很小，后续应扩展查询集，防止只对少量示例有效。

## 已知限制与下一步

第四阶段发现，复核模型如果看到早先被拒绝的答案和校验错误，可能反复否定已经修正的结果；对合理追问也可能过度拒绝。现将适用条件核验与答案复核分开，复核只接收当前答案和实际观察，对非回答终态保留确定性校验。复核仍可能犯错，不能成为唯一验收依据。

原生函数调用改善了动作结构，但不自动解决停止、证据缺漏或适用范围问题。合成资料增加可审查的配套引用关系后，执行器可以要求规则与替代依据同时读取和引用；关系标注本身不创造制度优先级，仍须原文支持。

更直接的教训是：上一批 26/26 自动通过后，AI 阅读答案仍发现模型擅自把“15 天”换算成具体日历日期，资料没有说明计日规则。保留该批问题记录、补充日期来源检查后重新运行，最终版本才作为当前证据。这说明自动化断言会有盲区；日期出现于来源也不能证明整句推论正确。

第四阶段固定版本 26/26 通过有限检查，但暂时工具故障 B08 两次仍未完成，说明保守失败与恢复能力应分开评价。第五阶段扩展案例后暴露新的问题，不能再把该历史数字用于当前实现。

第五阶段首次新增边界 0/8，涉及改写任务、从操作步骤推断即时耗时、历史错误答案影响复核、假设事件发生于新规之后。限制前置分类改写后又引入过早追问，最终将真实模式的指代判断放回同一工具循环。这个取舍减少一次调用，也避免前置分类成为独立故障点，但仍不能保证所有含糊问题均正确澄清。

最严重的新问题是模型已经检索到不同期限，却不声明冲突、只引用其中一份。只在模型自报冲突时校验不够，因此增加从实际候选检测同措辞数值差异的约束，要求读取双方并给出关系依据。该检查只发现有限结构，不能据此宣称所有文档冲突都能识别。

效果验证还要检查“问的问题对不对”和“引用跟哪项断言相连”，不能只看状态与原文子串。AI 审读发现某些澄清问错对象、替代声明与引用位置对应不清，即使有限自动检查通过也需另外记录。后续应扩展独立评测集和结构化关系标注，而不是持续针对同一组样例调整提示。

- 真实模型输出仍有随机性；引用文本存在不能证明结论完全受支持，版本日期、适用范围及替代关系需要逐项审查。
- 当前知识库小、中文词法检索有限；需增加陌生表达、长文档与更多冲突类型，比较检索方案。
- 规则完整性检查不能替代语义判断，部分文本检查针对中文表达，可能误拒绝其他表述。
- 超时只能停止本地等待，不保证远端生成已取消。当前只读 CLI 无生产级隔离和权限系统。
- 待补候选人个人验证与完整语义验收复核；用户已提供目标仓库，最终提交以交卷消息和实际Git结果为准。

## 第六阶段交付复盘

无密钥解压复现比在原目录重跑更能发现隐含依赖：原始运行记录使用Windows分隔符，离线审计需规范化路径；ZIP库又会规范化条目名称，危险路径检查应使用原始名称。新增8项交付测试验证了摘要、路径与已配置密钥泄漏阻断。112项测试及干净副本均通过，不代表模型语义问题消失。

交付中还需区分三种标识：引擎摘要对应业务源码字节，ZIP摘要对应包内容，Git SHA对应实际仓库提交。用`.gitattributes`保持检出字节一致，将最终Git SHA放在交卷消息中，避免在同一提交文件里写自身SHA造成版本循环。所有工作仍由AI实施，提交作者配置不能当作个人独立贡献的证明。
